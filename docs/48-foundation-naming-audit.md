# Foundation Naming Audit

**Status:** naming and vocabulary alignment against `docs/42–45`; no new mathematical abstraction is promoted by this note.

## 0. Purpose

The Process Geometry foundation now has a stable enough conceptual spine to audit the software vocabulary before attempting a deeper theory/implementation alignment.

The baseline is deliberately narrow:

- `42-process-geometry-from-distinguishability.md` — horizontal distinguishability geometry;
- `43-myhill-nerode-and-the-topological-threshold.md` — exact future equivalence versus topology;
- `44-objectification-semantic-compression-and-rank-lowering.md` — vertical ontology growth;
- `45-lineage-objectification-and-analytic-closure.md` — lineage and semantic/topological/analytic closure.

This pass asks only:

> Does a program name denote the same kind of object that the foundation now gives that word?

It does **not** ask whether the current implementation already realizes the full theory.

---

## 1. Reserved foundation vocabulary

The following words now have sufficiently specific theoretical roles that new code should not use them casually.

### Process

Primitive operations/transitions together with admissible composition and continuation. A particular coordinate realization is not the process ontology.

### History

A literal or suitably declared path/term generated by a process. History retains order/provenance until an explicit relation or semantic quotient removes it.

### Task

The declared semantics that determine which distinctions must be preserved. A task may be implemented through observations, predicates, certificates, future experiments, or another explicit oracle.

### Observer and observable

These are related but not synonyms.

- an **observable** is a quantity/expression read from a process state or history;
- an **observer** is a broader observation mechanism, protocol, family, or structured construction that determines distinguishability.

A scalar polynomial can be an observable used by an observer; renaming every `Observable*` class to `Observer*` would therefore be incorrect.

### Distinguishability

Whether allowed task/observer experiments can separate two process states or histories. Exact future distinguishability may generate a continuation-stable equivalence; finite-resolution distinguishability may instead generate neighborhoods/locality.

### Task continuation signature

A finite computational witness consisting of task observations under every allowed continuation through a bounded depth. It is evidence for bounded distinguishability, not a differential jet and not automatically the exact infinite future quotient.

### Task quotient / process quotient

Reserve these names for an actual quotient of process states/histories by a declared semantic equivalence such as

\[
\mathcal H(P)/{\sim_Q}.
\]

An algebraic elimination image of selected observables is a different object
and should be named an **observable algebraic image** or presentation.

### Presentation

An auditable task-sufficient realization of process structure. `representation` remains acceptable as an informal umbrella word, but concrete API objects that carry task semantics, relations, decoding, or cost should prefer `Presentation`.

### Semantic compression

Forgetting distinctions only under declared semantics. Ordinary simplification, common-subexpression elimination, memoization, or code shortening does not by itself deserve this name.

### Objectification

Promotion of a stable semantic process/object into a new reusable primitive. Under `docs/44`, objectification additionally matters because the new primitive opens a new compositional language whose legal composites remain grounded by compositional rank lowering.

Therefore a `PrimitiveProposal` is **not yet an objectification**. It is only a candidate that may later satisfy objectification gates.

### Process rank

Semantic/process abstraction level in the vertical tower. It is not currently identified with tensor rank, matrix rank, categorical dimension, polynomial degree, or implementation layering.

### Rank lowering

A composition-preserving semantic interpretation of a higher-rank language into an explicitly declared lower-rank semantic domain. It is stronger than string expansion or a per-symbol decoder.

### Analysis

Variation on induced process structures: local directions, flows, derivatives, observer paths/connections, limits, and global analytic structures when justified. This is why `jet` should be available for genuinely local/differential meanings rather than finite future enumeration.

## 3. Why `jet` is being retired from the finite future signature

The old `ProcessJetSignature` object stores

\[
\bigl(T(\operatorname{state}(hw))\bigr)_{w\in\Sigma^{\le k}},
\]

namely task observations over a bounded free continuation tree.

This is much closer to a finite Myhill–Nerode-style continuation signature than to a differential jet. `docs/43` now gives a precise vocabulary for this distinction.

The canonical API therefore becomes:

```python
from process_geometry.presentation.history import (
    TaskContinuationSignature,
    task_continuation_signature,
    history_task_continuation_signature,
)
```

The old names remain aliases during the 0.0.x transition so Sonnet 001 and historical notes retain executable provenance.

The word **jet** is thereby freed for a future structure that actually captures local/differential data if independent research forces such an abstraction.

---

## 4. Why observable elimination results are algebraic images

`discovery.polynomial` uses Groebner elimination to remove source variables and
expose relations among chosen observables. This produces a useful algebraic
presentation of the observable-map image.

It is not, by itself, the semantic quotient

\[
\mathcal H(P)/{\sim_Q}
\]

of the horizontal foundation.

Conflating these two notions would become dangerous as soon as the library implements a genuine distinguishability quotient/minimal presentation layer.

The public discovery surface therefore prefers:

```python
ObservableAlgebraicImage
discover_first_order_observable_image
search_first_order_observable_presentations
structural_first_order_observable_presentation_cost
```

while retaining historical backend names as compatibility aliases.

This is a naming correction, not a claim that the current polynomial backend has gained new semantics.

## 5. Primitive proposals versus objectification

The existing construction layer does something important but narrower than `docs/44` objectification:

- it preserves construction history;
- it bounds a grammar of candidate expressions;
- it assigns construction cost;
- it can feed candidates into presentation search.

It does **not** yet establish:

1. task-relative semantic stability of a new object;
2. a new higher-rank free composition language;
3. compositional rank lowering for all legal higher-rank composites;
4. relation soundness across rank;
5. semantic/topological/analytic closure.

Therefore `PrimitiveProposal` remains appropriate precisely because it says **proposal**, not `ObjectifiedPrimitive`.

A future Experimental objectification API should not be implemented by merely renaming this class.

## 6. Naming rules after this audit

For new code and docs:

1. Prefer **presentation** for an explicit task-sufficient computational realization; use **representation** only as an intentionally broad informal term.
2. Reserve **task/process quotient** for quotients by explicit semantic equivalence; qualify algebraic images, coordinate quotients, and elimination quotients.
3. Reserve **jet** for genuinely local/differential structure.
4. Distinguish **observer** (mechanism/protocol) from **observable** (quantity read by one).
5. Do not call a candidate primitive **objectified** until a higher-rank compositional language and coherent lowering semantics exist.
6. Do not use **rank** for arbitrary implementation layers when `process rank` is meant.
7. Keep backend names qualified (`ConstraintCanonicalization`, polynomial observer, Abelian analysis) until independent domains justify a generic abstraction.
8. Historical notes may retain old terminology when needed for provenance; current API/docs should state the canonical term explicitly rather than rewriting research history silently.

---

## 7. Deliberate non-goals

This audit does **not** create or promote:

- `ProcessGeometry`;
- `ObserverTopology`;
- `DistinguishabilitySpace`;
- `SemanticCompression` as a class;
- `Objectification` / `ObjectifiedPrimitive`;
- `ProcessRank`;
- `RankLowering`;
- `SemanticClosure`, `TopologicalClosure`, or `AnalyticClosure` APIs.

Those are theory/implementation alignment questions for the next stage and must pass the repository governance process.

The purpose of the present pass is smaller: prevent existing implementation vocabulary from pre-empting those meanings before the abstractions are actually earned.

---

## 8. Next stage after naming alignment

Once the terminology above has settled, the next question becomes structural rather than lexical:

> Which pieces of `docs/42–45` already exist in executable form, which are only shadows in current APIs, and which require genuinely new structures?

That later audit should map, at minimum:

```text
horizontal:
    distinguishability -> exact quotient -> locality/topology -> complexity -> analysis

vertical:
    free process -> semantic compression -> objectification
    -> higher-rank composition -> compositional lowering
```

onto concrete modules, missing interfaces, calibrations, and red teams.

No such structural promotion is implied by this naming note.

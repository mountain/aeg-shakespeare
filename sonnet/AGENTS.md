# Sonnet research protocol for agents

This file governs research work under `sonnet/`.

## Problem-native first

A Sonnet must not begin by inheriting the ontology of an existing solver, proof script, numerical package, or literature-standard coordinate system merely because that implementation is available.

Before optimizing or extending a baseline, perform a **problem-native primitive audit**:

1. state the mathematical task independently of the existing implementation;
2. identify the primitive processes/operations that generate the problem;
3. identify the observer/contact condition that defines success or failure;
4. list exact symmetries, actions, quotients, and history equivalences already forced by those primitives;
5. map those primitives to the strongest already-implemented Shakespeare structures before introducing generic substitutes.

Only after this audit may an existing solver state be used as a primary presentation.

## Arithmetic-first rule

If the problem is generated by Addition, Multiplication, their iterates, or explicit actions between their finite/continuous process families, test the A/M language first unless there is a concrete obstruction.

In particular, inspect:

- `aeg_shakespeare.analysis.am` / `aeg_shakespeare.function_theory.am` for continuous A/M process calculus;
- `aeg_shakespeare.process.finite.ProcessFamily` and `FamilyAction` for finite arithmetic shadows;
- process history / quotient machinery for task-relative state reduction;
- presentation search and cost/Pareto machinery for candidate selection.

Do not replace an A/M-native task by Fourier, spectral, vector-space, matrix, or generic linearized machinery unless the experiment explicitly establishes that the arithmetic presentation is inadequate or more expensive.

## Discovery before hand-supplied cleverness

When Shakespeare already has bounded proposal generation and presentation selection machinery, use it before inserting a known closed-form invariant by hand.

A useful invariant may be retained as a **hidden oracle/red-team target**, but it should not be an input to the discovery run if the research claim is that Shakespeare can discover representations.

Keep these roles distinct:

```text
primitive grammar       what the system is allowed to build with
exact task oracle       what must be preserved
candidate generator     what representations are proposed
certificate             why a proposed quotient is safe
cost model              why one safe representation is preferable
hidden known answer     post-hoc calibration only
```

## Staged search

For a problem with a strong native language, use two gates:

1. **native-language search** — restrict candidates to the strongest problem-native process family and determine how far it can compress the task;
2. **unrestricted search** — after freezing the native result, reintroduce competing presentation families and compare on the same task/cost semantics.

Do not conflate failure to dominate a pre-existing solver implementation with failure of the native mathematical language.  Solver bookkeeping may itself be representation baggage.

## Baseline solver discipline

Existing code is evidence and a benchmark, not ontology.

When crossing back to an upstream solver:

- construct an explicit presentation bridge;
- preserve exact outputs before claiming speedup;
- separate representation gain from implementation micro-optimization;
- keep open-problem instances as holdouts after first contact;
- do not tune a new presentation on the open frontier.

## CI discipline

Long-running Sonnet experiments are research benchmarks, not routine package regression tests.

- ordinary semantic/unit regressions should remain seconds-scale;
- multi-minute upstream benchmarks and open-case probes should be manually dispatched or otherwise explicitly requested;
- do not make expensive frontier experiments automatic PR gates;
- when adding a research test, measure or tightly bound its expected cost before allowing it into the default matrix.

## Research note requirement

For every substantial Sonnet phase, record:

- primitive assumptions;
- forbidden imported structures;
- task semantics;
- candidate presentation grammar;
- certificate/verification method;
- cost axes;
- red teams;
- claim boundary;
- what the experiment teaches about Shakespeare itself.

The final item matters: a Sonnet is not only a problem-solving attempt; it is also a calibration of the framework's ability to discover useful presentations.
